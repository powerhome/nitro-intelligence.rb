# nitro-intelligence.rb

`nitro_intelligence` is the Ruby client for the Nitro Intelligence Platform (NIP), published to rubygems.org. Rails applications use it to reach three NIP services, each defaulting to its shared production deployment in `lib/nitro_intelligence/configuration.rb`:

- **Inference Gateway** (LiteLLM, `https://inference.powerhome.ai`) through [`openai/openai-ruby`](https://github.com/openai/openai-ruby): chat, completions, embeddings, image generation and editing, audio transcription, text-to-speech and, through openai-ruby's generic `request`, System One decisions (`/v1/systemone`) and reranking (`/v1/rerank`). The gem reads gateway-specific response headers (`x-litellm-response-cost`, `x-litellm-call-id`) and sends `x-litellm-trace-id`, `x-litellm-spend-logs-metadata` and, for a Cerebro project that masks content, `x-litellm-enable-message-redaction`. The contract it relies on is the parent repository's [`docs/inference-gateway.md`](https://github.com/powerhome/nitro-intelligence/blob/main/docs/inference-gateway.md), [`docs/inference-pricing.md`](https://github.com/powerhome/nitro-intelligence/blob/main/docs/inference-pricing.md) and [`docs/client-observability-policy.md`](https://github.com/powerhome/nitro-intelligence/blob/main/docs/client-observability-policy.md).
- **Cerebro** (Langfuse, `https://cerebro.powerhome.ai`) through [`simplepractice/langfuse-rb`](https://github.com/simplepractice/langfuse-rb): tracing observed generations, prompt fetching with fallbacks, media upload and scoring. Cerebro is deployed from [`powerhome/cerebro`](https://github.com/powerhome/cerebro).
- **NIP Assistants** (Aegra/LangGraph, `https://assistants.powerhome.ai`) over HTTP: running assistant threads and resuming human-in-the-loop reviews of tool calls and replies. Assistants are served by [`powerhome/nip-assistants`](https://github.com/powerhome/nip-assistants).

User-facing documentation is `docs/README.md` (configuration and usage) and `docs/ASSISTANTS.md` (the Assistants API). Keep them in step with behaviour changes.

## Where changes live

- `lib/nitro_intelligence/configuration.rb`: configuration keys and their defaults, including the service base URLs.
- `lib/nitro_intelligence/client/`: the inference client. `handlers/` holds one plain handler per modality (chat, image, audio transcription, text-to-speech, decision, embedding, rerank) and `base_handler.rb` sets the gateway request headers; `handlers/observed/` holds the variants that trace to Cerebro; `observers/langfuse_observer.rb` records generations, cost and usage.
- `lib/nitro_intelligence/observability/`: Cerebro projects, per-project Langfuse clients, prompt resolution and fallbacks, media upload.
- `lib/nitro_intelligence/langfuse_extension.rb`, `langfuse_tracer_provider.rb`, `trace.rb`: extensions to langfuse-rb that allow several Langfuse clients (one per Cerebro project) in one process. Candidates for upstreaming to langfuse-rb.
- `lib/nitro_intelligence/assistants.rb`, `assistant.rb`, `assistant_registry.rb`, `run_result.rb`, `pending_review.rb`, `review_decision.rb`, `tool_call_review_interrupt.rb`, `tool_call_review_validator.rb`: the NIP Assistants client, run results (including the reply's delivery status) and the review protocol for tool calls and replies (`__reply__`).
- `lib/nitro_intelligence/models/`: the model catalog built from `model_config` and the per-modality default models.
- `lib/nitro_intelligence/media/`: image and audio inputs and image generation results.
- `spec/`: RSpec suite, mirroring `lib/` under `spec/lib/`. HTTP is stubbed with WebMock.
- `spec/e2e/`: end-to-end specs, the client against the real inference gateway and Cerebro with nothing stubbed. Tagged `:e2e`, which `spec_helper.rb` excludes from every run but `rake e2e`. They make billable calls, so they assert only what any working model gets right (a relevant document ranks first, speech transcribes back to its words), never exact wording, and keep to small, cheap requests. `spec/e2e/e2e_helper.rb` holds their model configuration.
- `nitro_intelligence.gemspec`: runtime dependencies. `langfuse-rb` is pinned exactly and `openai` has a floor that the gemspec comment justifies; check upstream behaviour at the pinned version before relying on it.
- `doc/dependency_decisions.yml`: license_finder approvals, checked in CI.

## Development

- `bin/setup` runs `bundle install`. Ruby 3.3 is the minimum and the CI version.
- `bundle exec rake` runs the RSpec suite, RuboCop and `rake yard`, which is what CI runs. `rake yard` fails on any undocumented part of the public API and on any YARD warning.
- `bundle exec rake e2e` runs the end-to-end specs against the shared gateway. It needs a gateway key in `NIP_E2E_INFERENCE_API_KEY` and, for the tracing specs, the Cerebro project's `NIP_E2E_OBSERVABILITY_PROJECT_ID`, `NIP_E2E_OBSERVABILITY_PUBLIC_KEY` and `NIP_E2E_OBSERVABILITY_SECRET_KEY`. It fails rather than skips without them, and takes `NIP_E2E_INFERENCE_BASE_URL` to aim at another gateway. Run it when a change alters what the client sends or how it reads a response; the unit suite stubs every request and cannot catch a mismatch with the gateway.
- The public API is what the YARD reference documents: every class, module, method and constant not tagged `@api private`, which `.yardopts` hides from the reference. It follows Semantic Versioning. Tag any new class, module or method that callers should not use `@api private`, and document everything else with YARD (`@param`, `@return`, `@raise`), which `rake yard` enforces. `docs/README.md` and `docs/ASSISTANTS.md` are guides to using the gem; cover what callers need there, but they need not list every public method. Before making something private, check that no consuming application calls it; one that does makes it public in practice. `bundle exec yard doc` writes the reference to `doc/api/`.
- `bundle exec rubocop` runs only the linter, with `rubocop-powerhome`; `.rubocop_todo.yml` holds existing exclusions.
- `bin/console` opens IRB with the gem loaded, and loads a git-ignored `.console_setup.rb` if present (a place for local credentials and `NitroIntelligence.configure`).

## CI and release

- `.github/workflows/nitro_intelligence.yml` runs on every push and calls the shared `powerhome/github-actions-workflows` `ruby-gem.yml` workflow: `bundle exec rake` on Ruby 3.3, plus a license_finder check against `doc/dependency_decisions.yml`.
- `.github/workflows/e2e.yml` runs `rake e2e` on every PR from a branch of this repository (fork and Dependabot PRs, which cannot read its secrets, skip it), on pushes to main, on weekday mornings (to catch a gateway-side change when nothing here is moving) and on demand. It runs on this repository's own self-hosted runner from PAC (`addons/releases/other-runners/tier/beta/nitro-intelligence-rb-runner.yaml` in `powerhome/pac`, label `pac-v2`), because the gateway is served only to Power's network. Since the repository is public and a fork PR runs its own copy of the workflow, fork-PR workflows need a maintainer's approval for every outside contributor (the repository's Actions setting, which `powerhome/software` cannot manage); keep it that way while the runner exists. Within the repository the boundary is write access: anyone who can push a branch can change the workflow or the specs and run that code on the runner, inside Power's network, with the `NIP_E2E_*` credentials. That is accepted because write access is held only by Power developers, granted through `powerhome/software`, and the credentials are scoped to a budgeted gateway key and a test-only Cerebro project. The runner is ephemeral (ARC's default, which `nitro-intelligence-rb-runner.yaml` keeps): each job gets a fresh pod, so nothing a job installs or leaves behind reaches the next one. Revisit this if the credentials ever grow beyond those two. Its credentials are the `NIP_E2E_*` repository secrets and the `NIP_E2E_OBSERVABILITY_PROJECT_ID` variable, which `powerhome/software` provisions and writes (the `ai-ruby-sdk-e2e` project in `application.nitro-intelligence.tf`) rather than anyone setting them by hand: a gateway key of its own with a monthly budget, so the suite's spend is capped and shows separately in the gateway's spend logs, and a key for the "Ruby SDK End-to-End Tests" Cerebro project, which keeps the suite's traces out of every application's project. Rotate them by replacing the resources there.
- A release is the PR that `.github/workflows/release.yml` opens with [release-please](https://github.com/googleapis/release-please) after every push to main, or refreshes if it is already open, whenever `feat`, `fix` or breaking changes have merged since the last release. It bumps `lib/nitro_intelligence/version.rb`, updates `Gemfile.lock` to match, and adds a `docs/CHANGELOG.md` section built from those PRs' titles. It is assigned to whoever merged PRs since the last release. Leave it unmerged to hold a release back. Nobody writes it by hand, and cutting a release is not an agent's job: asked for one, point to the open release PR rather than bumping the version, editing the changelog's generated sections or tagging.
- The version comes from the titles merged since the last release: a breaking change (`!`, or a `BREAKING CHANGE:` paragraph in the description) is a major bump, `feat` a minor one, and `fix` or `perf` a patch. Other types release nothing and stay out of the changelog. A PR with more than one change consumers see lists the others as `feat:` or `fix:` lines of their own at the bottom of its description, which becomes the squash commit's body. Put migration steps for a breaking change in its `BREAKING CHANGE:` paragraph or the ASSISTANTS.md "Upgrading" sections, since the changelog entry is one line. To correct a merged PR while its release is still pending, add a `BEGIN_COMMIT_OVERRIDE` block to its description listing every change it should contribute; a `Release-As: X.Y.Z` line in a commit body forces a version. [release-please's docs](https://github.com/googleapis/release-please#how-should-i-write-my-commits) cover both. release-please reads the override marker anywhere in a PR description, even inside backticks, and replaces the commit with whatever follows it, so a PR that only mentions the marker releases nothing. Write the marker in a description only to open an override block, and call it a commit override block otherwise. Settings are in `release-please-config.json`, and the last released version in `.release-please-manifest.json`.
- Once the release PR merges, the same workflow publishes the GitHub release `vX.Y.Z` on its squash commit, with that version's changelog section as its notes, and tags the same commit `vX.Y.Z-nitro_intelligence`. That tag's push runs `nitro_intelligence.yml`'s `release` job, which runs only for refs containing `refs/tags/v` and the package name `nitro_intelligence`; it runs `rake build release:guard_clean release:rubygem_push`, publishing to rubygems.org with the organisation's `RUBYGEMS_API_KEY` secret. release-please finds the last release by its own `vX.Y.Z`, so both tags stay. Changelog sections from before release-please are the hand-written Keep a Changelog history.
- `release.yml` authenticates as a GitHub App (`RELEASE_APP_CLIENT_ID` variable, `RELEASE_APP_PRIVATE_KEY` secret) with contents and pull requests write. The variable and secret live in the `release` environment, which only `main` can deploy to, so a workflow run from a branch or tag cannot read the key. A job that mints an App token declares `environment: release`; never add them as repository secrets or variables. It cannot use `GITHUB_TOKEN`, because a PR or tag that token creates starts no workflows: the PR would never get its required checks, and the tag would never publish the gem. The App also signs the release commit, which main's ruleset requires.
- There is no staging or production deployment of this repository. A release reaches NIP's users when a consuming application bumps `nitro_intelligence` in its `Gemfile.lock` and deploys. Known consumers are `powerhome/nitro-web` (configured in `config/initializers/nitro_intelligence.rb`, with components declaring the dependency in their gemspecs) and `powerhome/tempo`.
- `agentic-pr-review.yaml` runs an automated review on PRs; the `agentic-review-opt-out` label skips it. `reviewdog.yml`, `stale.yml` and `.github/CODEOWNERS` are managed by `powerhome/software` and are overwritten from there.

## Nitro Intelligence Platform

This repository is one part of the Nitro Intelligence Platform (NIP). The parent repository is [`powerhome/nitro-intelligence`](https://github.com/powerhome/nitro-intelligence). The full set of NIP repositories and the upstream projects they build on, and where each kind of change lands, is in [`docs/operations/repositories.md`](https://github.com/powerhome/nitro-intelligence/blob/main/docs/operations/repositories.md) there. When planning or executing work, consider that whole set: check whether a change here depends on, or requires, a change in a sibling repository, and whether the behaviour in question is actually decided upstream (for this repo, chiefly `openai/openai-ruby` and `simplepractice/langfuse-rb` at the pinned version, and the LiteLLM, Langfuse and Aegra/LangGraph APIs of the services it calls). Name cross-repository follow-ups explicitly in the plan or PR.

## Pull requests

- Title every PR as a [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/), `type(scope)!: description`, as NIP's [decision record](https://github.com/powerhome/nitro-intelligence/blob/main/docs/operations/decisions/0002-conventional-commits-drive-nip-releases.md) sets out: `feat` or `fix` for changes this repository's consumers see, other types for the rest, and `!` with a `BREAKING CHANGE:` paragraph in the description for a breaking change. A Runway key, if there is one, goes in square brackets at the end. The title becomes the squash commit on `main`, and the `PR title` check enforces the format.
- Never open a pull request ready for review. Always open it as a draft (`gh pr create --draft`). A ready PR notifies reviewers and CODEOWNERS immediately, so opening one early takes other people's attention before the PR is ready for it.
- Mark a PR ready for review only when all of these are done: robot code review has run and every finding has been addressed, either fixed or answered; any deployment or manual testing the change needs has been done and its results recorded on the PR; and the PR's owner has finished their own review.
- If a PR is opened ready by mistake, put it back to draft with `gh pr ready --undo <number>`.
- The release PR that release-please opens is the one exception, and opens ready for review. It only adds the changelog section and bumps the version, and merging it is how whoever merged since the last release accepts the release, so a draft would add the step the automation exists to remove.
- When an agent opens a PR on someone's behalf, that person owns it and decides when it is ready. The agent leaves it in draft and says when it is ready for the owner's review.
